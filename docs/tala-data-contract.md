# TALA Data Contract (Resort Operations)

Scope: the SAME `TallaAgent` powers the guest orb, Admin, and the staging
worker. All operational truth lives in **Supabase** tables (or D1 for the few
local-only domains). TALA reads and writes through repository functions in
`worker/src/db/repos/*` — there are **no scattered direct Supabase calls inside
tool code**. This keeps the future swap to our own Postgres/API clean: only the
repo layer changes.

Conventions
- Primary ID: `UUID` (Supabase `gen_random_uuid()` default) — **never shown to a guest**.
- Guest linkage: `guest_name` / `guest_phone` (the operational tables carry these columns).
- Short human references: `MT-YYYYMMDD-XXXX` (room), `TT-XXXX` (tour), `MR-XXXX`
  (rental), `HK-XXXX` (housekeeping), `PAY-XXXX` (payment). Generated by the
  repo, persisted where the table has a `reference` column.
- Lifecycle/status vocabulary: `requested | pending | confirmed | in_progress |
  preparing | ready | delivered | completed | cancelled | checked_in |
  checked_out | settled`.
- Financial truth: prices are looked up from backend catalogs (menu, tour
  catalog, motorbike table). Guest/model-supplied prices are **never** trusted.

## Authoritative tables

### bookings (Supabase)
- Purpose: confirmed room stays / reservations (operational truth for rooms).
- Primary ID: `id` (UUID).
- Guest linkage: `guest_name`, `guest_phone`.
- Status: `pending | confirmed | checked_in | checked_out | cancelled`.
- Financial: `amount`, `paid_amount`.
- TALA tools: `getGuestStay` (read), `checkRoomAvailability` (read-only conflict check), `checkInGuest`/`checkOutGuest` (owner PATCH status).
- Supabase dep: yes (REST).
- Notes: check-in/out is the authenticated admin flow; guests cannot self-settle.

### tala_booking_requests (Supabase)
- Purpose: guest room-booking intents awaiting owner confirmation.
- Primary ID: `id` (UUID). Reference: `reference` (`MT-…`).
- Guest linkage: `guest_name`, `guest_email`, `guest_phone`.
- Status: `pending` (→ owner confirms in Admin).
- TALA tools: `requestRoomBooking` (write), `findPendingBooking` (dedupe).
- Supabase dep: yes.
- Notes: `20260811_booking_request_contact.sql` (run by David) adds
  `guest_email`/`guest_phone`/`reference`.

### tala_tour_requests (Supabase)
- Purpose: tour/activity requests.
- Primary ID: `id` (UUID). Reference: `reference` (`TT-…`, added by `20260812_tala_lifecycle_references.sql`).
- Guest linkage: `guest_name`, `guest_phone`, `guest_email` (added by 20260812 migration).
- Status: `requested` (default) → `confirmed`/`cancelled` in Admin.
- Financial: `amount` (authoritative, from `tours_catalog` D1 price).
- TALA tools: `requestTour` (write, authoritative price), `findPendingTour` (dedupe), `getGuestTourRequests` (read).
- Supabase dep: yes. Pricing source: **D1 `tours_catalog`** (`getTourPrice`).

### tala_rental_requests (Supabase)
- Purpose: motorbike rental requests.
- Primary ID: `id` (UUID). Reference: `reference` (`MR-…`, added by `20260812_tala_lifecycle_references.sql`).
- Guest linkage: `guest_name`, `guest_phone`, `guest_email` (added by 20260812 migration).
- Status: `requested` (default) → `confirmed`/`cancelled`.
- Rate source: **Supabase `motorbikes.daily_rate`** (`getBikeRate`) — not persisted on the request.
- TALA tools: `requestRental` (write), `findPendingRental` (dedupe), `getGuestMotorbikeState` (read, joins `motorbikes` for live rate).
- Supabase dep: yes (requests + rate lookup).

### tala_food_orders (Supabase)
- Purpose: food & drink orders.
- Primary ID: `id` (UUID). Reference: `reference`.
- Guest linkage: `guest_name`, `guest_phone`.
- Status: `pending | confirmed | preparing | ready | delivered | cancelled`.
- Financial: `total`, `total_cost`, `paid_amount`. Items JSONB carry
  `{menuItemId, name, quantity, price, foodCost}` — **price from D1 `menu_items`**.
- TALA tools: `createFoodOrder` (write, authoritative price), `getGuestFoodOrders` (read).
- Supabase dep: yes. Pricing source: **D1 `menu_items`**.

### tala_guest_messages (Supabase)
- Purpose: guest ↔ reception inbox (operational messages).
- Primary ID: `id` (UUID).
- Guest linkage: `guest_name`, `guest_phone`.
- Status: `unread | read | replied`.
- TALA tools: `writeGuestMessage` (owner/TALA write), `getGuestMessages` (read).
- Supabase dep: yes.

### tala_folio_lines (Supabase) — billing truth
- Purpose: itemized guest bill. Charges + explicit payments.
- Primary ID: `id` (UUID).
- Guest linkage: `guest_name`, `guest_phone`.
- Key fields: `kind` (`charge | payment`), `category` (`room | tour | rental |
  food | service | other`), `amount`, `method`, `reference`, `related_type`,
  `related_id`.
- Integrity rules: links are explicit (`related_type`/`related_id`); unlinked
  lines are reported as `unresolved`, never guessed. Balance = Σcharges − Σpayments.
- TALA tools: `getGuestFolio` (read + balance), `recordPayment` (owner write, `kind=payment`).
- Supabase dep: yes.

### guest_requests (D1) — local-only domains
- Purpose: housekeeping, maintenance, and generic requests that have **no
  Supabase table yet**.
- Primary ID: `id` (UUID). Reference: tool-generated `HK-…` (not persisted as a column).
- Guest linkage: `guest_name`.
- Status: `pending | confirmed | completed | cancelled`.
- TALA tools: `requestHousekeeping` (write, deterministic), `createMaintenanceRequest`, `createGuestRequest` (generic).
- Supabase dep: **no** — D1 only.
- Notes / migration path: when we move to our own backend, housekeeping should
  get a real Supabase/Postgres table so it stops being a `guest_requests` row
  and joins the unified `getGuestStayState` without the D1 fallback.

### motorbikes / motorbike_rentals (Supabase) — inventory + active rentals
- Purpose: bike fleet + currently active rentals.
- TALA read: `getGuestMotorbikeState` joins `motorbike_rentals` → `motorbikes` for live rate.
- Supabase dep: yes.

### tours_catalog (D1) — tour price source
- Purpose: authoritative tour catalog + price.
- TALA read: `getTours`, `getTourPrice`.
- Supabase dep: **no** (D1). Migration note: pricing should live behind the same
  repo interface so it can move to Postgres without touching tools.

### menu_items (D1) — food price source
- Purpose: authoritative menu + price.
- TALA read: `getMenu`, `createFoodOrder` (price lookup).
- Supabase dep: **no** (D1).

## Unified read: getGuestStayState
Composes `bookings`, `tala_tour_requests`, `tala_rental_requests`,
`tala_food_orders`, `tala_guest_messages`, `guest_requests` (housekeeping), and
`tala_folio_lines` into one object with `phase` (before_arrival / checked_in /
staying / checkout_approaching / checked_out) and `outstanding` actions. No
record duplication — every field maps to exactly one authoritative source.

## Future backend migration notes
- All Supabase access is isolated in `worker/src/db/repos/guestStateRepo.ts`
  (and sibling repos). Swapping to our own Postgres/API means reimplementing
  these repo functions behind the same exported signatures.
- Tools call repo functions, never raw `fetch` to Supabase — keep it that way.
- `cms_data` remains content/config only, never transactional truth.
- Operational truth must never live in `localStorage`.
